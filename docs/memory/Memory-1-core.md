## Decisions made (with reasons)
- 2026-09-08 · **Reservations are the placement stock check** (manager, 2.4): `reserveForOrder` runs inside the placement transaction after the order lines exist, under one `SELECT … FOR UPDATE` over the variants' level rows in canonical order (variant id → warehouse priority → warehouse code) — every placement locks in the same order, so overlapping placements queue instead of deadlocking (8-parallel test in shuffled line order) and the last unit goes to exactly one (race test). The cart's add-time check stays advisory. Greedy allocation by priority is Phase 2's policy; window 11 plugs a smarter one behind the same function.
- 2026-09-08 · **A reservation is not a movement**: `reserved` moves, `on_hand` and the ledger do not, no event. `on_hand` changes only through `moveStock`; below zero only via `sale` (a shipped backorder). Backorderable variants reserve past availability (`available` negative = the backorder).
- 2026-09-08 · **Release on cancel is the orders module's job** (`releaseForOrder` inside `cancelOrder`, before the transition), never window 8's; consumption on shipment is window 8's call (`consumeForShipment`: reservation → `sale` movement per warehouse, over-consumption 409).
- 2026-09-08 · **Void on failure** (#174 review): every step of `completeCart` after a successful `authorize` runs under a guard that calls `PaymentProvider.void` before rethrowing — a shortfall from the reservation, a shipping-option race or a DB error leaves no dangling hold (tested on the manual provider's call log; a successful placement never voids).
- 2026-09-08 · `listInventoryLevels`' `x-permission` is `viewer` on `store:{store_id}` with an OPTIONAL query: with `store_id` the object is that store (store-scoped client); without it `store:*` and the caller's visible stores (RLS). The admin router's generic `permission(op)` cannot express this (`{store_id}` ≠ `{storeId}`), so the route uses `requirePermission` with its own object factory.
- 2026-09-08 · **One transition function, table-driven** (manager, 2.3): `STATUS_TRANSITIONS` / `PAYMENT_TRANSITIONS` / `FULFILLMENT_TRANSITIONS` are the source of truth, the README shows them and a test asserts equality; every status change goes through `transition()`; a guard test fails on any `UPDATE "order"` outside the module. Events: `status` → `order.confirmed`/`order.cancelled`/`order.completed` (processing → `order.updated`), payment/fulfillment/edits → `order.updated` with `changed_fields`. Exactly one event per call.
- 2026-09-08 · **Wrappers are idempotent on the target state** (a webhook retry from window 7/8 is not a 409); `transition()` itself is strict (no self-loops in the tables). No auto-confirm at placement: `pending` is a real state until an operator or window 7's capture confirms. Payment failure changes only `payment_status`. `markShipmentCreated` needs `confirmed` (pending → processing is illegal).
- 2026-09-08 · **Cancel voids, never refunds**: `cancelOrder` only while unfulfilled; authorised payments go through `PaymentProvider.void` (manual no-op; Stripe cancels the intent) and the payment row → `cancelled`; captured money is window 7's on `order.cancelled`. A failed void → 402, nothing written.
- 2026-09-08 · **Edits leave money alone**: totals recomputed with the cart's `TaxCalculator`, the delta appended to `order.metadata.edits[]` for window 7; no Admin API operation exists → module functions + CONTRACT CHANGE #172 (`PATCH`/`DELETE …/orders/{id}/line-items/{lineItemId}`, store_admin).
- 2026-09-08 · **Idempotency keys stored as `<store_id>:<key>`** in `payment.idempotency_key`: the column is UNIQUE table-wide while RLS hides other stores' rows from the replay lookup, so a key reused by another store hit a unique-violation 500 (caught by the per-store test the manager asked for). No schema change; window 7 splits on the first `:` if it needs the raw key.
- 2026-09-08 · Other modules' Admin routers mount through `src/http/module-routers.ts` (`moduleAdminRouters()`, after `adminRouter()`; `mountCoreMiddleware({ moduleRouters })` for tests) — the named mount point for window 9's `merchandisingRouter` (#162 part 3); the list is empty until search 2.2 lands.
- 2026-09-08 · The Store order read moved from checkout to orders; checkout imports `renderStoreOrder` back (a benign module cycle — functions used inside functions only).
- 2026-09-08 · **Idempotency = `payment.idempotency_key`** (manager decision, 2.2): placement creates exactly one payment row and 0006 already makes the column UNIQUE. Replay reads the order through it and never calls the provider again (test proves one `authorize` call). No idempotency table, no column on `"order"`, no metadata pollution. The same key on another cart is a 409 `conflict` (never another cart's order).
- 2026-09-08 · **Display id via the existing store-row trigger** (`app.assign_order_display_id()`: `UPDATE store … RETURNING` inside the insert = row lock on the store row). Concurrent placements serialise per store and cannot collide (8 parallel → consecutive). Per-store serialisation is a Phase 3 scaling concern (recorded in the checkout README), not now.
- 2026-09-08 · A payment session is required to complete; `manual` is never assumed (a storefront that skips the step cannot place unpaid orders). `POST …/payment-session` again replaces the session with the current total (the storefront does this right before completing).
- 2026-09-08 · `GET /store/orders/{id}` answers only 200 or 404 (contract): invalid token, unknown customer, wrong email, other store → 404; the email is trimmed + lowercased for the comparison; no log line carries the email or the query string (test with console spies). `order.customer_id` = `cart.customer_id` (window 13 sets it); the storefront client never sends the customer token to cart paths.
- 2026-09-08 · The order read model (`renderOrder`, `getStoreOrder`) lives in checkout until 2.3 creates `src/modules/orders`; the cart module exports its internals (`loadCart`, `lockActiveCart`, `loadLines`, `recalculate`, `renderCart`, `assertLinesInStock`, row types) for checkout only — both are window 1's, same tables, same transaction.
- 2026-09-08 · **Carts bypass Medusa's cart module** (owner decision deferred from 1.8; manager accepted at the start of 2.1). The contract cart is `public.cart`/`cart_line_item`: `organization_id`+`store_id`, RLS, integer minor units, `metadata` round-trip, everything `order.placed` needs; Medusa's cart lives in schema `medusa` with no tenant scoping, no outbox, another shape, and our routes already answer ahead of Medusa's. Consequence: **no Medusa mirror of stores/channels/keys is needed at all** — the 1.8 mirror question is closed, `src/bootstrap` stays a read-only verifier. Recorded in `src/modules/cart/README.md` "Decisions"; the manager mirrors it in Memory-main.
- 2026-09-08 · Tax and shipping pricing sit behind module-public interfaces (manager requirement): `TaxCalculator.calculate(ctx)` → per-line `{ taxRateBp, taxMinor }` + `shippingTaxMinor`; `ShippingRateProvider.list/quote(ctx)`. Defaults read our tables through the mutation's `tx`. Windows 7 (#127) and 8 (#130) call `setTaxCalculator`/`setShippingRateProvider` at boot and never edit the module. Prices are tax-exclusive in Phase 2 (tax-inclusive display = later store setting). Line tax display derives from the persisted `tax_rate_bp`; cart total uses the calculator's amounts (a provider with its own rounding may differ by a minor unit on the line display; `order_line_item.tax_minor` is exact at placement).
- 2026-09-08 · `currency` query on product reads: validated against `store_currency` (400 `validation_error` `{ currency: "one of …" }`, malformed → `ISO 4217 code, e.g. EUR`), default the store default currency; the read model already drops products without a price in that currency. Promotion codes: accepted, trimmed, de-duplicated case-insensitively, stored; discount 0 until window 9's promotions public API exists (`recalculate()` gets a third provider call then).
- 2026-09-08 · A shipping option that is no longer quotable after a country change is dropped silently (shipping → 0) instead of failing the PATCH; setting an unavailable option explicitly is a 400. `express.json` is mounted on `/store/carts` only, after the read routes and before the fallback proxy.

## Gotchas learned
- Medusa 2.20.1 requires Node `^20.19 || >=22.12` (it relies on `require(esm)`; our workspace packages are ESM-only). Local Node is 20.19.1: OK.
- Workspace packages export `dist/` only: build `@platform/db|events|contracts` before running core outside turbo.
- `.claude/CLAUDE.local.md` is gitignored (root .gitignore line 7); it is per-worktree and never committed.
- Seed script and RLS test already live in packages/db (Phase 0); Next items 1.3 and 1.8 are narrowed to issues #3 and #8.
- `gh pr close --delete-branch` deletes the LOCAL branch too (not only the remote): keep a tag or another ref on the commits first.
- Postgres is on **5433** (5432 belongs to another project on this machine); CI uses 5432. `vitest.config.ts` defaults to 5433, env wins.
- Medusa vs our migrations ordering: `pnpm db:migrate` (packages/db, owner) first, then `pnpm --filter @platform/core db:medusa:migrate`; they are independent schemas, but the Medusa script needs the `platform_app` role that 0001 creates.
- Medusa's link sync swallows errors (`executeWithConcurrency` → settled promises) and still logs "Created following links tables"; verify `medusa.link_module_migrations` has ~20 rows. The empty-message failure we hit was `permission denied for database` (MikroORM DDL begins with `create schema if not exists`).
- Medusa runs a "create defaults" workflow at boot (Medusa default store, sales channel, publishable key in `medusa.*`); task 1.8 must map ours onto that rather than fight it.
- `Error: Cannot find module 'ts-node'` printed once during `db:medusa:migrate` comes from the forked search-index child; harmless (the child still ran).
- Medusa's own `/admin` auth still answers `401 {"message":"Unauthorized"}` for paths we have not implemented as route files (e.g. `/admin/me` before 1.7): our middleware passed, Medusa's did not. Our route files must `export const AUTHENTICATE = false`.
- `apps/core/eslint.config.mjs` is only used by `pnpm --filter @platform/core lint`; ESLint 9 does not pick up nested flat configs from the root run, and the root config is main-window owned.
- Seed data already has one primary domain per store (`shop.<code>.local`), a `web` sales channel and one publishable key; tests that add domains/keys must count relative to that.
- Ajv: compiling an operation's `requestBody.schema` object standalone breaks its `#/components/...` refs (MissingRefError). Compile `{ $ref: '<docId>#/paths/<escaped path>/<method>/requestBody/content/application~1json/schema' }` instead (JSON-pointer escaping `~0`/`~1`).
- Never put JS with backticks inside a bash double-quoted `node -e "…"`: the shell runs the backticks as commands and silently mangles the edit. Write the script with the Write tool and run `node <file>`.
- `medusa build` leaves `apps/core/.medusa/server/**` (gitignored) which the ROOT `pnpm format:check` / `pnpm lint` still scan → REQUEST #72 (root ignore lists); until then `rm -rf apps/core/.medusa` before running the root gates. `apps/core/eslint.config.mjs` ignores it locally.
- `medusa build` evaluates `medusa-config.ts` through ts-node without a database: keep the config throw-free (loud placeholders) and enforce env in `src/server.ts`.
- Keycloak realm JSON changes (e.g. #65, conditional OTP) need `node infra/keycloak/reimport.mjs staff` + a Keycloak container restart, or `pnpm dev --reset` (wipes the shared Postgres volume — avoid while other windows run). Core Phase 1 tests do not touch Keycloak (dev tokens).
- Package-local `pnpm --filter @platform/core typecheck|test` fails with "Cannot find module @platform/auth-sdk" until the workspace packages are built (`pnpm turbo run build --filter=...`); the root turbo commands and CI build them first.
- After the manager merges another window's work into main, `git merge main` alone is not enough: run `pnpm install` (new deps of THEIR packages, e.g. auth-sdk's `jose`) and rebuild the workspace packages, or `apps/core` typecheck/tests fail inside their modules (`hq-rbac`) with "has no exported member" / "X is not a constructor".

The admin uses `ADMIN_API_URL`.

- `db:medusa:migrate` under tsx: Medusa's loaders `register()` ts-node (installed since #60) behind tsx, and ts-node then type-checks tsx's transpiled CommonJS of `medusa-config.ts` (TS7006 on "line 2") and the run reports a failure AFTER the module migrations succeeded (exit 1). `TS_NODE_TRANSPILE_ONLY=1` (set by the script) makes the ts-node hook a pass-through; verified exit 0, "Medusa schema ready".

- body-parser errors (malformed JSON) are plain Errors with `type: 'entity.parse.failed'`, `expose: true`, `status`; `coreErrorHandler` maps `entity.*` + `expose` to the contract 400 — before 2.1 they rendered as 500 `internal` (the admin routes never noticed because their tests send valid JSON).
- Under RLS a cart of another store is simply absent: every cart operation of store B on store A's cart is a 404, never a 403 — the tests assert exactly that; do not "improve" it to 403 (it would leak cart ids across stores).

- `src/lib/attribution.ts` reads touches as `{ utm_source, utm_medium, utm_campaign, utm_term, utm_content, referrer, landing_path, at | captured_at }`; a touch with only `source`/`medium` keys is "empty" and yields NO row (tolerant by design). Test fixtures must use the `utm_*` keys.
- Postgres infers `$1` as uuid when first compared to a uuid column: `aggregate_id = $1 OR payload->>'order_id' = $1` fails with "operator does not exist: text = uuid" — cast (`$1::text`) when one parameter meets two types.
- Ports 9000 and 3000 were already in use on this machine by other processes (another window's core / something else): run a second core with `PORT=9010` and the storefront with `next dev --port 3101`; never kill a process you did not start. The storefront needs `STORE_PUBLISHABLE_KEY=pk_brand-a_dev_…` explicitly (its default `pk_test_storefront_starter` gets a 401 from the core) and `STORE_API_URL`.
- `next/image` in the storefront refuses the seeded thumbnails' host (`picsum.photos`): the storefront UI cannot show the real catalogue until window 3 allows the host (#109 comment). Verify core journeys with the curl replay (`scratchpad/journey.sh` pattern: store → products → cart → line-items → shipping-options → PATCH → payment-session → complete ×2 → orders?email) and the core log's `store api fallback →` lines.
- Two concurrent `tx.query` on one pg client (`Promise.all`) trigger pg's "client.query() when already executing" deprecation warning (catalog's `loadAggregates` does it, pre-existing); keep new code sequential inside a transaction.

- prettier re-pads markdown tables: a test that asserts README lines must collapse runs of spaces first (orders.test.ts does), and doc patch scripts must not anchor on table padding — anchor on a cell's content or insert before a line prefix.
- `payment.idempotency_key` is UNIQUE across all stores (0006); anything "per store" on that column has to be encoded in the value. The store-scoped replay lookup alone is NOT enough — the insert still collides.
- The cross-module cycle orders ⇄ checkout (`paymentProvider` one way, `renderStoreOrder` the other) is fine under CommonJS because nothing is used at module-evaluation time; keep it that way (no top-level calls across the boundary).
- Vitest picks up `src/modules/search/*.test.ts` (window 9) in the core suite now; `search-live.test.ts` skips without `ALGOLIA_*`.

- pg infers untyped CASE branches (`CASE … THEN $3 ELSE $4 END`) as text: cast them (`$3::int`) or the UPDATE fails with "column is of type integer but expression is of type text".
- To test a placement-time stock failure the cart must be built while stock suffices (the cart's add-time check would refuse first), then stock lowered before `completeCart`.
- A generated column (`inventory_level.available`) reads stale inside the same transaction only if you keep an old row object: re-read after the UPDATE or track the delta locally (reservations.ts adjusts its in-memory copies).

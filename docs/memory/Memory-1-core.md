  1. **Module `src/modules/inventory`** (`index.ts`, `service.ts`, `reservations.ts`, `read-model.ts`, `types.ts`, `README.md`, `inventory.test.ts`). Tables are all in 0007: `inventory_level` (`available` GENERATED = on_hand − reserved), `stock_movement` (append-only for `platform_app`: 0009 revokes UPDATE/DELETE), `reservation` (order_id | cart_id, `released_at`). No schema change needed.
  2. **Movements are the only way `on_hand` changes**: `moveStock(tx, { variantId, warehouseId, delta, reason, reference?, actor, note? })` locks the `inventory_level` row (`FOR UPDATE`; creates it at 0 when missing), applies `on_hand += delta`, inserts the `stock_movement` row and emits exactly one `stock.moved` v1 (`stock_movement_id`, `variant_id`, `sku`, `warehouse_id`, `delta`, `reason`, `reference_type/id`, `on_hand_after`, `reserved_after`) in the same transaction. A guard test: no `UPDATE inventory_level` / `INSERT INTO stock_movement` outside the module. Test that the app role cannot UPDATE/DELETE `stock_movement` (permission denied).
  3. **Reservations** (`reservations.ts`): `reserveForOrder(tx, { orderId, storeId, lines: [{ variantId, quantity }] })` — per line, lock the variant's `inventory_level` rows in active warehouses ordered by `warehouse.priority` (`FOR UPDATE`, deterministic order = no deadlocks), allocate greedily across warehouses, insert one `reservation` row per (line, warehouse), `reserved += q`. Short and `allow_backorder = false` → 409 `out_of_stock` `{ variant_id, available }` (contract) and the whole placement rolls back; `allow_backorder = true` → reserve anyway in the priority warehouse (`available` goes negative = the backorder; `backorder_quantity` in the result). `manage_inventory = false` → no reservation. A reservation is NOT a movement (`on_hand` unchanged, no `stock.moved`). `releaseForOrder(tx, orderId)` — cancel: `reserved −= q`, `released_at = now()`, idempotent. `consumeForShipment(tx, { orderId, lines: [{ lineItemId | variantId, warehouseId?, quantity }] })` — window 8 at ship time: `reserved −= q`, then `moveStock(reason 'sale', reference order)` for `on_hand −= q` (one `stock.moved` per line/warehouse); over-consumption beyond the reservation → 409. `restockFromReturn` (2.5) = `moveStock(reason 'return')`. All exported for windows 8 / task 2.5 with a scoped client + ids only.
  4. **Wire placement and cancel**: `completeCart` (checkout) calls `reserveForOrder` right after the order lines are inserted and before the payment row (replaces the cart module's `assertLinesInStock` re-check at placement: the reservation IS the check under the row lock); `cancelOrder` (orders) calls `releaseForOrder` before the transition. The cart's add-time check stays as is (advisory, `available` already subtracts reservations). **Concurrency test (acceptance)**: two placements racing for the last unit → exactly one 201, the other 409 `out_of_stock`; both through `completeCart` on separate connections (`Promise.all`).
  5. **Availability read model**: the catalog read model already sums `inventory_level.available` over active warehouses (`in_stock`, `available_quantity`, `allow_backorder`) — reservations reflect automatically; test: a placed order lowers the Store API's `available_quantity` by the ordered quantity and `in_stock` flips at 0 (backorderable stays `in_stock`). Quantity buckets: the Store contract's Variant has `in_stock` + `available_quantity` (nullable) — no extra bucket field exists in 0.3.0; nothing to add.

## Decisions made (with reasons)
- 2026-09-08 · **One transition function, table-driven** (manager, 2.3): `STATUS_TRANSITIONS` / `PAYMENT_TRANSITIONS` / `FULFILLMENT_TRANSITIONS` are the source of truth, the README shows them and a test asserts equality; every status change goes through `transition()`; a guard test fails on any `UPDATE "order"` outside the module. Events: `status` → `order.confirmed`/`order.cancelled`/`order.completed` (processing → `order.updated`), payment/fulfillment/edits → `order.updated` with `changed_fields`. Exactly one event per call.
- 2026-09-08 · **Wrappers are idempotent on the target state** (a webhook retry from window 7/8 is not a 409); `transition()` itself is strict (no self-loops in the tables). No auto-confirm at placement: `pending` is a real state until an operator or window 7's capture confirms. Payment failure changes only `payment_status`. `markShipmentCreated` needs `confirmed` (pending → processing is illegal).
- 2026-09-08 · **Cancel voids, never refunds**: `cancelOrder` only while unfulfilled; authorised payments go through `PaymentProvider.void` (manual no-op; Stripe cancels the intent) and the payment row → `cancelled`; captured money is window 7's on `order.cancelled`. A failed void → 402, nothing written.
- 2026-09-08 · **Edits leave money alone**: totals recomputed with the cart's `TaxCalculator`, the delta appended to `order.metadata.edits[]` for window 7; no Admin API operation exists → module functions + CONTRACT CHANGE #172 (`PATCH`/`DELETE …/orders/{id}/line-items/{lineItemId}`, store_admin).
- 2026-09-08 · **Idempotency keys stored as `<store_id>:<key>`** in `payment.idempotency_key`: the column is UNIQUE table-wide while RLS hides other stores' rows from the replay lookup, so a key reused by another store hit a unique-violation 500 (caught by the per-store test the manager asked for). No schema change; window 7 splits on the first `:` if it needs the raw key.
- 2026-09-08 · Other modules' Admin routers mount through `src/http/module-routers.ts` (`moduleAdminRouters()`, after `adminRouter()`; `mountCoreMiddleware({ moduleRouters })` for tests) — the named mount point for window 9's `merchandisingRouter` (#162 part 3); the list is empty until search 2.2 lands.
- 2026-09-08 · The Store order read moved from checkout to orders; checkout imports `renderStoreOrder` back (a benign module cycle — functions used inside functions only).
- 2026-09-08 · **Idempotency = `payment.idempotency_key`** (manager decision, 2.2): placement creates exactly one payment row and 0006 already makes the column UNIQUE. Replay reads the order through it and never calls the provider again (test proves one `authorize` call). No idempotency table, no column on `"order"`, no metadata pollution. The same key on another cart is a 409 `conflict` (never another cart's order).
- 2026-09-08 · **Display id via the existing store-row trigger** (`app.assign_order_display_id()`: `UPDATE store … RETURNING` inside the insert = row lock on the store row). Concurrent placements serialise per store and cannot collide (8 parallel → consecutive). Per-store serialisation is a Phase 3 scaling concern (recorded in the checkout README), not now.
- 2026-09-08 · A payment session is required to complete; `manual` is never assumed (a storefront that skips the step cannot place unpaid orders). `POST …/payment-session` again replaces the session with the current total (the storefront does this right before completing).
- 2026-09-08 · `GET /store/orders/{id}` answers only 200 or 404 (contract): invalid token, unknown customer, wrong email, other store → 404; the email is trimmed + lowercased for the comparison; no log line carries the email or the query string (test with console spies). `order.customer_id` = `cart.customer_id` (window 13 sets it); the storefront client never sends the customer token to cart paths.
- 2026-09-08 · The order read model (`renderOrder`, `getStoreOrder`) lives in checkout until 2.3 creates `src/modules/orders`; the cart module exports its internals (`loadCart`, `lockActiveCart`, `loadLines`, `recalculate`, `renderCart`, `assertLinesInStock`, row types) for checkout only — both are window 1's, same tables, same transaction.
- 2026-09-08 · **Carts bypass Medusa's cart module** (owner decision deferred from 1.8; manager accepted at the start of 2.1). The contract cart is `public.cart`/`cart_line_item`: `organization_id`+`store_id`, RLS, integer minor units, `metadata` round-trip, everything `order.placed` needs; Medusa's cart lives in schema `medusa` with no tenant scoping, no outbox, another shape, and our routes already answer ahead of Medusa's. Consequence: **no Medusa mirror of stores/channels/keys is needed at all** — the 1.8 mirror question is closed, `src/bootstrap` stays a read-only verifier. Recorded in `src/modules/cart/README.md` "Decisions"; the manager mirrors it in Memory-main.
- 2026-09-08 · Tax and shipping pricing sit behind module-public interfaces (manager requirement): `TaxCalculator.calculate(ctx)` → per-line `{ taxRateBp, taxMinor }` + `shippingTaxMinor`; `ShippingRateProvider.list/quote(ctx)`. Defaults read our tables through the mutation's `tx`. Windows 7 (#127) and 8 (#130) call `setTaxCalculator`/`setShippingRateProvider` at boot and never edit the module. Prices are tax-exclusive in Phase 2 (tax-inclusive display = later store setting). Line tax display derives from the persisted `tax_rate_bp`; cart total uses the calculator's amounts (a provider with its own rounding may differ by a minor unit on the line display; `order_line_item.tax_minor` is exact at placement).
- 2026-09-08 · `currency` query on product reads: validated against `store_currency` (400 `validation_error` `{ currency: "one of …" }`, malformed → `ISO 4217 code, e.g. EUR`), default the store default currency; the read model already drops products without a price in that currency. Promotion codes: accepted, trimmed, de-duplicated case-insensitively, stored; discount 0 until window 9's promotions public API exists (`recalculate()` gets a third provider call then).
- 2026-09-08 · A shipping option that is no longer quotable after a country change is dropped silently (shipping → 0) instead of failing the PATCH; setting an unavailable option explicitly is a 400. `express.json` is mounted on `/store/carts` only, after the read routes and before the fallback proxy.
- 2026-09-04 · Medusa's own tables go in Postgres schema `medusa` (`projectConfig.databaseSchema`): Medusa's core modules declare `product`, `store`, `sales_channel`, `cart`, `order`… — the same names as our frozen schema in `public`. Our data stays in `packages/db` tables under RLS; Medusa's built-in tables carry no contract data in Phase 1.
- 2026-09-04 · Custom server entry (`src/server.ts`) instead of bare `medusa start`: Medusa's publishable-key middleware is applied to the whole `/store` namespace by the framework `ApiLoader` (no per-route opt-out), expects header `x-publishable-api-key` plus a row in Medusa's `api_key` table, and answers 400 `{type}` instead of the contract's 401 `{code}`. Middleware mounted before Medusa's loaders runs first (Express order). Admin routes opt out of Medusa auth with `export const AUTHENTICATE = false` and use our `requirePermission` stub.
- 2026-09-05 · **Owner decision, supersedes the 2026-09-04 mirror plan:** the Medusa mirror (our stores → Medusa sales channels + publishable keys) is **deferred to the Phase 2 cart task**, where we decide whether carts use Medusa's cart module behind our contract routes or bypass Medusa's Store API entirely. Not built speculatively. Task 1.8 = idempotent fail-fast verifier only (no Medusa-side rows); the contract routes need nothing from Medusa because they answer ahead of its key gate (#57).
- 2026-09-04 · Medusa migrations run as a dedicated role `medusa_owner` (owns schema `medusa`, CREATE on the database, no rights on our tables), not as the owner role: Medusa module migrations probe `information_schema.tables` for `public.product`/`public."order"` (v1 upgrade check) and fail on ours; a role without privileges on them does not see them. Runtime stays `platform_app` (granted on `medusa.*` by default privileges).
- 2026-09-04 · `search_path` pinned via `projectConfig.databaseDriverOptions` (`searchPath` + `connection.options`): `databaseSchema` alone is not honoured by Medusa's raw-SQL migrations (24 tables leaked into `public` before this).
- 2026-09-04 · Workspace ESM packages are loaded from this CommonJS app with dynamic `import()` (`initDb()`), because their export maps lack a `default`/`require` condition → issue #40. `medusa-config.ts` stays free of `@platform/*` imports.
- 2026-09-05 · Admin API routes: `adminRouter` mounted ahead of Medusa (same reasons as the Store API). Permissions and request schemas come from `admin-api.yaml` itself at runtime (`src/http/openapi.ts`) so route code cannot drift from the contract; `requirePermission` is a Phase 1 stub over `role_assignment` per ADR 0002 (owner ⊇ all; store_staff ⊂ store_admin; org relations reach every store; `viewer` = any relation) behind the signature auth-sdk implements. Reads (`GET`) also go through the same permission check.

- Never put JS with backticks inside a bash double-quoted `node -e "…"`: the shell runs the backticks as commands and silently mangles the edit. Write the script with the Write tool and run `node <file>`.

## The two known bottlenecks

**1 — the app pool (four connections per `GET /store`, `DB_POOL_MAX` = 10).** At the target load the pool
never saturated: at most 8 (run A) and 6 (run B) of its connections were busy at once, 0% of samples saturated.
With `GET /store` alone, run B's ramp held **50 and 100 req/s at p95 20 ms** with at most 4–5 connections busy;
the 200 req/s step began seconds before the laptop suspended, so **the pool's knee is above 100 req/s of
`GET /store` and is not measured on the laptop** — the GitHub-runner run below is the second attempt at it. Arithmetic, not measurement: 10 connections ÷ 4
per request = at most 2 `GET /store` in flight at once; anything beyond waits inside the core, where Postgres
cannot see it. **Recommendation for window 1 (no change made here):** find out why `GET /store`
checks out four connections (whether its reads can share one), or raise `DB_POOL_MAX` with the database's
`max_connections` in view — with the knee from the runner's ramp as the number to size against.

**2 — the store-row lock on placement.** `app.assign_order_display_id()` (migration 0006) updates the store row
inside the order insert and holds it until `completeCart` commits, so one store's placements serialise. At the
target (30/min) Postgres saw **no lock wait** in either run. On one store the placement ramp held **every step up to
240 orders/min** in run A (complete p95 65–97 ms) and run B (complete p95 118–130 ms), with no lock wait sampled;
run B's 480 and 960 steps are void (suspend). Serial floor from the target runs: `complete` p50 66 ms (A) / 71 ms
(B) → even fully serial, one store places ~840–913 orders/min; the measured ceiling on this laptop is above
240/min, i.e. **≥ 8× the target**.

## Read this before the numbers

- **Laptop, not server.** Intel Core Ultra 7 155H (22 logical cores), 31 GB RAM, Windows 11; the core, Postgres,
  Redis and k6 (in Docker Desktop) all share it. The GitHub-hosted runner is the second datapoint — not a
  production server either.
- **The laptop was on battery and went into Modern Standby during run B's two ramps** (Windows Kernel-Power
  506/507: 12:22–12:23, 12:23–12:41, 12:48–13:17, 13:17–14:03 UTC). The report generator now finds such gaps in
  the Postgres sampler and marks every step from the first one on as **void**; those steps are kept in run B's
  tables for the record only and carry no conclusion. A third attempt (11:16) slept through its target phase
  and was discarded entirely. Run A and run B's target phase had no gap.

## What Grafana would need

- **Traces and request metrics from the core:** an OpenTelemetry SDK in `apps/core` exporting to the collector
  the observability profile already runs (`infra/observability`); today the core exports nothing, so these
  numbers come only from k6 and `pg_stat_activity`.
- **Pool metrics:** the app pool's `totalCount`, `idleCount` and `waitingCount` (node-postgres exposes all
  three) as gauges — the waiting count is the saturation Postgres cannot see.
- **Postgres:** `postgres_exporter` (connections by state, lock waits, `pg_stat_statements`).
- **k6:** `--out experimental-prometheus-rw` to the stack's Prometheus, so a run lands on the same dashboards.

### Bottleneck 1 — the app pool (four connections per GET /store)

The core's app pool is `DB_POOL_MAX` = 10 connections (role `platform_app`). Sampled once a second from `pg_stat_activity` during the target run (614 samples):

- connections held by role `platform_app`: max **16** — more than `DB_POOL_MAX` when it is, because more than one pool in the core connects as that role; the request pool is the one capped at 10;
- busy (active or idle in a transaction): max **8**, mean 1.6;
- **saturated** (every pool connection busy) in **0.0%** of samples.

With four connections per `GET /store`, 10 connections serve at most 2 such requests at once; every further request waits for a connection inside the core, which Postgres cannot see — it shows up as latency on the routes above, not as waits here. Top wait events: `Client:ClientRead` ×5.

### Bottleneck 2 — the store-row lock on placement

Every order takes its store's row lock: migration 0006's trigger `app.assign_order_display_id()` runs `UPDATE store SET next_order_number … RETURNING` inside the order insert and holds it until `completeCart` commits, so one store's placements serialise on the rest of that transaction (lines, payment, reservations, attribution, outbox).

During the target run Postgres saw lock waits in 0.0% of samples (max 0 sessions waiting at once, mean 0.00).

**Serial bound:** `complete` took p50 66 ms / p95 111 ms in the target run. Even if every placement held the store row for its whole `complete` request, one store could place about **913 orders/min** at p50 latency (539 at p95) — 17× the target. The lock is held only from the order insert to the commit, so the true ceiling is above that.
